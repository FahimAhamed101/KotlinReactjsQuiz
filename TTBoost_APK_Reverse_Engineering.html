4. How requests are secured

Two independent mechanisms, both of which our port reproduces:

a. HMAC request signing

The app signs every call. Header names recovered from the DEX:

X-Timestamp      seconds (or ms) — must be within ±60s of the server
X-Nonce          one-shot random value, replay-protected
X-Signature      HMAC-SHA256 of  "{METHOD}|{path}|{timestamp}|{nonce}|{json}"
hash             sha256(HASH_VALUE) — a static second factor
X-App-Token      the session token
X-Username       the linked TikTok handle
X-App-Version-Code
X-Captcha-Token  when a captcha is required
X-Firebase-AppCheck
X-Signature-Resync-Retry / X-Token-Refresh-Retry   retry markers

Because the timestamp is validated against the server clock, the app ships a ttboost_server_clock string and calls server-time — a device with a skewed clock would otherwise have every request rejected.

b. The signing key lives in native code

lib/arm64-v8a/libnative-lib.so exports Java_com_ttboost_tik_tok_followers_likes_security_NativeSecretProvider_getSecretKey. The HMAC secret is computed inside the .so and returned over JNI, so it never appears as a plain string in the DEX. That is a deliberate anti-tamper measure: the key cannot be read with a simple string dump, only by disassembling the native library.

c. Anti-fraud and integrity

  • Emulator / root detection — strings such as “Virtual disk partitions detected”, “VirtualBox / Hyper-V / KVM kernel modules present” and “Virtualization properties found” come from a VirtualDetector class.
  • Firebase App Check (Play Integrity / reCAPTCHA Enterprise) plus a X-Firebase-AppCheck header.
  • Google reCAPTCHA and an X-Captcha-Token header.
  • Bugfender for remote logging.

5. The coin / task economy — how it actually works

This is the part that matters for our bugs. The loop is:

1. A user BUYS a boost (e.g. 100 followers).
        -> an order row is created with status = Progress

2. That order is served to OTHER users in their feed  (me/orders)
        -> each viewer sees "@someone +5 coins"

3. The viewer taps Follow  -> the app opens TikTok on that profile
        -> the user follows, returns to TTBoost

4. The app calls  coins/check  with the order id
        -> the server decides whether the action really happened
        -> if yes: +N coins to the viewer, order progress +1

5. When progress reaches the target the order completes and the
   buyer has received their followers.
Key insight: the coins are paid by the platform, and the followers are delivered by other real users. There is no “instant follower” API anywhere in this APK — a 100-follower order completes only when 100 different people do the task. That is the design, not a missing feature.

How the server verifies a follow (the important bit)

The DEX contains an incremented field used by coins/check. Our port originally treated that field as proof: if the client said follow_incremented: true, coins were credited immediately without contacting TikTok. Since the Android client hard-coded that flag to true, every tap on Follow paid out — which is precisely the bug you reported.

The correct check, which our server now performs, is a counter comparison:

anchor  = the viewer's own "following" count, snapshotted when the feed was served
current = the viewer's live "following" count, fetched now
if (current > anchor)  -> a follow really happened -> pay
else                   -> nothing happened          -> pay nothing

Likes work the same way, against the target video’s like count.

9. What this analysis changed in our code

  1. Removed the client-trusted payout. coinsCheck.verifyFollow and verifyLike no longer short-circuit on follow_incremented / likes_incremented; they compare live counters instead.
  2. Stopped the client asserting completion — verifyTask() no longer sends those flags.
  3. Prime the like baseline. A like can only be verified against a “before” snapshot, so the app now calls POST /v6/posts/url before opening TikTok. The reference app does the same thing through its ChooseVideo flow.
  4. Fixed the seed crash that left the feed empty (freeFollowers is not defined).
  5. Stopped scraping TikTok on every feed load — the anchor is now reused for 10 minutes, which cut the feed from 3.8 s to 1.5 s.
  6. Raised the client timeout from 12 s to 30 s so a cold serverless start no longer surfaces as “Could not load tasks”.
